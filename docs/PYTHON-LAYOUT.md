# Python layout

Where the Python code lives, what each module owns, and how to add a new one
without breaking a layout guard. Read this before adding, moving, or renaming
a Python module.

## Package structure

`hub.py` remains the command launcher and compatibility facade. The engine lives in `skill_hub/`.

| Directory | Responsibility |
|---|---|
| `skill_hub/domain/` | Rules, models, validation, classification, and calculations |
| `skill_hub/application/` | Sync, reconciliation, import, restore, and other operations |
| `skill_hub/infrastructure/` | Persistence, native configuration, subprocesses, and network transport |
| `skill_hub/entrypoints/cli/` | Command registration and dispatch |
| `skill_hub/entrypoints/mcp/` | MCP control-plane requests |
| `skill_hub/hub_core.py` | Shared legacy functions and state, pending a separate responsibility split |

Each layer groups modules by subject. Move a mixed module according to its main responsibility. This layout does not enforce clean dependency directions yet.

Use qualified package imports. Keep the existing facade bindings and function-local `import hub` where required. Do not add root-level domain modules.

The Tauri resource map ships `skill_hub/` recursively. Tests inspect nested modules and preserve the existing leaf-import restrictions. New modules must join a mutation group. Update the explicit mypy selection when appropriate.

`skill_hub/application/backup/recovery.py` owns machine-local restore progress,
source recovery, repository selection, checkout attachment, and final local sync.
`skill_hub/entrypoints/cli/recovery.py` registers the thin `hub recovery` interface.
`skill_hub/application/backup/references.py` validates internal file references for backup and restore.
These modules ship through the existing recursive package resource mapping.

The complete move inventory is [moves.json](changes/DESIGN-python-package-layout/moves.json). File moves preserve function bodies, data formats, and command behavior.

### Layout guards to widen on every move

A move or rename that changes a module's name or location must widen
every text-scanning guard below in the same PR. Never delete an entry a move
stopped matching — widen the pattern instead:

- `bundle.resources` in `app/src-tauri/tauri.conf.json`.
- `CODE_HOME_DIRS` in `app/src/test/cliContract.test.ts`.
- The isolated package copy in `tests/test_selfcheck.py`.
- The recursive leaf checks in `tests/test_hub_split_guard.py`.
- The rerun list in `app/src-tauri/build.rs`.
- `MOCK_FILES` in the ipcParity test suite.

Silencing a guard instead of widening it is how a real regression slips
through a green run. Waves 20 and 25 of the `hub.py` split both tripped these
guards and both were fixed by widening, not by relaxing them.

Lives here, not `skill_hub/domain/diagnostics/risks.py` or `hub.py`, so the monolith's own doctor leg stays three lines. See "How hub reports MCP delivery" in `docs/SKILL-SCHEMA.md`.
- `skill_hub/infrastructure/mcp/mcp_probe.py` — the MCP liveness probe, a leaf (stdlib + `mcp_spec`/`hub_core`/`mcp_catalog` only): `resolved_env` (the hub process env, with a once-per-process login-shell snapshot filling in anything the GUI-launched process does not already see — `hub mcp check` and `MCP_UNRESOLVED_SECRET_REF` both read it), `probe`/`probe_all` (the stdio subprocess handshake and the http/sse `urllib` POST handshake — `initialize` then `tools/list`, protocol `2025-06-18` with one automatic retry at `2024-11-05` on a `protocol_error` at `initialize` only; a `${VAR}` that cannot resolve short-circuits before anything is spawned or sent; a stdio child is always killed and reaped, even on timeout), the per-id JSON-RPC response correlation (`_read_response` drains notifications/stray lines/other-request responses under one deadline instead of matching by pipe position), and the on-disk cache at `<data_home>/state/mcp/probes.json` (`read_probe_cache`/`write_probe_cache`/`delete_probe_cache_row`/`cache_age_summary`). `probe(...)` returns `(row, record | None)` — with `catalog=True` (the default for a single-name `hub mcp check`, never for `--all` or `hub mcp add --probe`) it also optimistically calls `resources/list`/`resources/templates/list`/`prompts/list` (+ paginated `tools/list`) after a successful `tools/list`, treating JSON-RPC `-32601` as "not offered" and everything else as a `fetch_errors` entry — once `tools/list`'s result is in hand there is exactly ONE exit and it is the `ok` row, whatever the catalogue calls do. This is the **only** module that opens a real connection to an MCP server — `hub sync`'s doctor leg imports the module (transitively, via `mcp_delivery`) but never calls `probe`/`probe_all`, and `resolved_env`'s login-shell snapshot only runs lazily, the first time a delivered spec references an unset `${VAR}` with no default (`MCP_UNRESOLVED_SECRET_REF`) — an ordinary sync with no such server spawns nothing. `forget_server(name)` deletes both the probe-cache row and the catalogue file together — every removal path (`skill_hub/entrypoints/cli/archive.py::cmd_archive`, `hub mcp reconcile --apply`'s `remove`, a `source_missing` drop) calls it. See "How hub reports MCP delivery" in `docs/SKILL-SCHEMA.md`.
- `skill_hub/infrastructure/mcp/mcp_catalog.py` — the MCP capability-catalogue PAYLOAD, a leaf (stdlib + `hub_core`/`mcp_spec` only; never `hub`): the record shape (`build_record`, `summarize` for the `<catalog summary>` that rides the probe row), JSON-Schema parameter flattening one level deep (`flatten_parameters` — `schema_unreadable`/`parameters_truncated`, a scalar `default` kept INCLUDING falsy `false`/`0`), sanitising server-authored text (`sanitize_text` — strips control characters, collapses newlines, bounds to `TEXT_LIMIT`), and the one-file-per-server store at `<data_home>/state/mcp/catalogs/<name>.json` (`catalog_path` calls `hub_core.validate_slug` BEFORE building any path — a hand-edited registry key is a live traversal vector). Every `uri`/`uri_template` is redacted through `mcp_spec.redact_url_secrets`. Pure and synchronous — no fixture server needed to unit-test it.
- `skill_hub/infrastructure/mcp/mcp_reconcile.py` — discover MCP servers already configured natively and classify them for `hub mcp reconcile`, a leaf (stdlib + `mcp_spec`/`hub_core`/`permissions`/`harnesses` only; never `hub`). `DiscoveredMcp` + `discover_native(scope_kind, project_cfg, registry, installed, harness_filter=None)` (one reader per native shape — Claude's `~/.claude.json` **user** `mcpServers` and **local** `projects.<abs>.mcpServers`, project `.mcp.json`, Codex `[mcp_servers.*]` at both scopes, opencode's project `mcp` object and its global `~/.config/opencode/opencode.json` `mcp` object — read but never importable) and `classify(discovered, registry, managed_names) -> list[<candidate row>]`, checked in this order: `already_managed` → `unsupported` → `stale` → `conflict`/`new` (unsupported outranks stale, so a registered-but-inactive `ws`/`oauth` entry still says why it can never come back). Per-harness shapes `mcp_spec.parse_native` cannot see on its own (Codex's `auth = "oauth"` value, `http_headers_helper`; opencode's `{"type":"local"|"remote",...}`) are pre-normalized into the generic shape here, then always handed to `parse_native`. `_no_global_writer`/`_is_active` treat Claude's own `"user"` scope label as a global-scope signal (Claude's top-level `mcpServers` IS the global scope_kind; a claude-family entry resolved to `pi` — no `Harness.global_mcp_config` — correctly gets `unsupported/no_global_target` instead of silently classifying `new`). Every discovery payload REDACTS a literal-secret value: known secret keys AND flagged URL query-string parameters (`_redact_url`) in `sources[].native` and `spec`/`options[].spec`/`options[].scope`/`options[].file` alike, INCLUDING an `unsupported` row that has no `spec` at all (`_redact_native_blind`, scanned directly with `mcp_spec.looks_like_secret`) — `skill_hub/entrypoints/cli/mcp.py`'s apply path re-derives the real, unredacted spec from the raw `DiscoveredMcp` list (never from a `classify()` row) when it actually needs to write one. A `conflict` option row carries `harness`+`scope`+`file` (Claude local vs. project shares a harness id; scope is what tells them apart). `managed_names(...)` reads the project sidecar through the representative-harness rule (`permissions.read_sidecar(..., kind="mcp")`, claude-code then pi) plus the FOUR global-MCP sidecars (claude-code, pi, codex, opencode, symmetric with the project-scope reader) directly by path convention. Every `_discover_*` calls `mcp_spec.normalize_native` directly (never raises — no per-entry try/except needed, closes the whole-file-dies-on-one-bad-entry crash), an unparseable native file surfaces as one `unreadable_file` row named after the file, `classify` groups candidates by the CASE-FOLDED SLUG (`mcp_spec.slugify_server_name`) rather than the raw native name, every row gains an `import_name` field (`sources[].name` keeps the native key verbatim), and `invalid_name`/`name_taken:<slug>` (a leftover `mcp-servers/<slug>/` dir counts too) are decided here, not only at apply time.
- `skill_hub/entrypoints/cli/mcp.py` — `hub mcp add|set|show|list|remove|check|catalog|reconcile`: registers a server you ALREADY have, by flags or by pasting its native JSON — a different job from `hub new mcp <name>` (`skill_hub/entrypoints/cli/skill.py`, scaffolds a brand-new Python server with generated code) and from `hub mcp-control` (`skill_hub/entrypoints/cli/mcp_control.py`, registers the Skill Hub control-plane server itself). `--all` defaults to `--no-catalog`, `--catalog` opts in; `--catalog-timeout-s` bounds the whole-catalogue fetch separately from `--timeout-s`); `add --probe` runs one check right after registering, always `catalog=False` (`"probe"` in the JSON payload is the resulting row, not always `null`); `show --json` reads the same probe cache back as `"last_probe"`. `catalog <name>` is read-only and NEVER probes — it prints the last-fetched `<catalog record>` (or a fail-closed `{"ok":false,...,"code":"no_catalog"}`) from `mcp_catalog.read_catalog`. `reconcile` (mirrors `hub permissions reconcile`) discovers via `mcp_reconcile` (validating `--harness` against `harnesses.HARNESSES`), then either prints/returns the candidate set (+ the `state/reconcile/<scope>.mcp.kept.json` kept-store names, `.mcp` kind suffix on the permissions precedent) or, with `--apply --decisions-stdin`, runs `_reconcile_apply_mcp` — one transaction: validate + resolve every decision first (a `conflict` decision matches its option on the `(harness, scope)` pair with `file` as a tiebreaker; a name already registered under a NON-mcp-server type fails closed naming the collision) so a bad one leaves nothing written; snapshot the registry `skills`/`projects` blocks, the scope's native files, EVERY `sources[].file` any resolved decision names, and every sidecar path a claim will touch; mutate; `save_registry` + a SCOPE-LIMITED sync (`mcp_sync.sync_mcp_for_project` / `mcp_sync._run_global_mcp_dispatch` — never the whole-registry `hub._auto_sync()`, the same scope-limited precedent `skill_hub/entrypoints/cli/permissions.py`'s `_sync_scope_native` follows) — skipped entirely (`"synced": false`) when the batch has no `import`/`remove`; on any failure, roll back everything (registry, files, sidecars, a just-created `mcp-servers/<name>/` folder) and re-raise — under `data_home_lock()` with one manual `append_audit("mcp-reconcile-apply", …)` record (a discovery-only run stays silent). `import` on an "unclaimed" conflict option (`harness: "registry"`) leaves the registry's own spec untouched and calls `_claim_unclaimed_native_entry` to write the sidecar (or sidecars — every differing native option, not just the first) immediately, rather than erroring on a duplicate name; the response's `suggested_refs: [{name,key,var}]` names the `${VAR}` a `replace_with_ref` import suggested. `remove` (stale candidates only) deletes the native entry via `_mcp_remove_native_entry` — backup-first + atomic + trailing-newline-preserving for every harness (the same pair `mcp_delivery.write_claude_approval` uses), collecting a failure into the summary's `errors[]` instead of swallowing it.

## Home resolution

`data_home()` resolution order: `$SKILL_HUB_HOME` then `$SKILL_HUB_DIR`
(legacy, deprecated, one-shot warning) then `~/.skill-hub/`. With no env and
no `~/.skill-hub/registry.yaml`, a legacy `~/Dev/.skill-hub/` is used
transparently with a migration prompt.

`code_home()` resolution order: `$SKILL_HUB_CODE`, then walk up from
`Path(__file__).parent` for a directory with `hub.py` and `app/`. In packaged
builds the Tauri side reads `<App>.app/Contents/Resources/hub/`.
